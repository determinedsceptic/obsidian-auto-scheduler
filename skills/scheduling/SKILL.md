# Scheduling

Allocate time only when the user explicitly asks to schedule, arrange, plan, or reserve time. A request to record, copy, rewrite, or organize note content alone does not authorize time allocation.

## Procedure

1. Read the relevant source content and constraints before planning. Preserve the user's existing wording and document organization. Headings and paragraphs are arbitrary user organization; do not infer a task category from a heading name.
2. Every new flexible task needs a persistent, user-visible unchecked, untimed checkbox (`[ ]`) outside Day planner. If it already exists, read and bind that checkbox; do not create a duplicate source. If it is missing, stage that checkbox with `stage_note_changes`. Then call `read_note` with the target `documentRef`, `mode: "document"`, and the staged result's `changeSetRef`. Use the returned checkbox `blockRef` as `plan_schedule.sourceRef`, pass the exact same `changeSetRef` to `plan_schedule`, and commit the combined change set once.
3. An existing task that is already bound may use `sourceRef: null`; the host retains its current binding. A selected legacy task with no binding must be explicitly bound to a read checkbox block before it can be scheduled. Do not match or bind by title alone.
4. Use `bind_task_source` for an existing task whose source must be bound or rebound. Its arguments are `{taskId, sourceRef, changeSetRef, title}` where `changeSetRef` is the exact staged edit reference for that `sourceRef` or `null`, and `title` is the new title or `null`. It is a stage-only operation: it changes no time allocation and preserves the task ID, budget, and history. After a source rename or move, read the staged document, pass its new checkbox `blockRef` and the same staged `changeSetRef` to `bind_task_source`. To schedule in the same transaction, pass the binding result's `changeSetRef` to `plan_schedule` and use `sourceRef: null` for that now-bound existing task. Commit the final combined change set once.
5. Pass a known total effort as `minutes`. Pass genuinely unknown total effort as `minutes: null`; do not substitute the configured default, infer a total from a deadline, or invent an estimate.
6. An unknown-effort task may be scheduled only after the user explicitly agrees to both `rollingMinutes` and `dailyMinutes`. `rollingMinutes` is the amount to reserve for the planning horizon or agreed cadence, and `dailyMinutes` caps the amount on one day. They describe scheduling budget and pace, not total effort, remaining effort, completion, or a finish date. A single agreed session is valid, for example `rollingMinutes: 30` and `dailyMinutes: 30`. If either value is unconfirmed, save the source only and ask one focused question for the missing budget and pace.
7. Call `plan_schedule` with only constraints supported by the request or returned context. Do not invent deadlines, durations, recurrence, priorities, availability, budgets, or daily pace.
8. Treat the schedule result as a proposal or staged change according to the tool result. If it returns edits to save, use the normal staging and commit workflow and rely on the final commit receipt.
9. If required information is contradictory or the scheduling tool reports that work cannot fit, explain that result or ask one focused question. Do not turn an unavailable slot into a successful schedule.
10. Report concrete times only after the applicable tool result confirms them. Preserve warnings, unscheduled items, conflicts, and partial failures. Give separate counts for persistent source checkboxes, scheduled session blocks, and pending or unscheduled budget; never present several sessions as several source tasks. For unknown total effort, state that no total or finish date was inferred.

Scheduling creates or updates dated session blocks; it never authorizes relocation, deletion, or completion of the source or unrelated note content. Explicit note edits remain allowed independently of scheduling. If such an edit detaches an obsolete source binding, retain its task/history, allocate no new time for that goal, and explicitly bind a read source before resuming it. Existing detached sessions can remain or yield to hard commitments without invented replacements. Completion with `[x]` and cancellation with `[-]` remain supported; never delete or complete a source merely because sessions exist.

## Calendar certainty and buffers

- Fixed appointments (travel, meetings, classes, reservations) and explicitly requested preparation or recovery time take precedence over unfinished recurring habits and flexible task sessions. Numerical importance is separate from certainty: raising a habit's priority does not make its preferred time a fixed commitment.
- Read the relevant calendar, then call `plan_schedule` with the exact event. Do not refuse merely because a habitual or movable activity occupies that time. The host retains unaffected habits, omits overlapping occurrences, and reallocates flexible task sessions where possible. An event-only call may use empty `tasks` and `habitRefs`; existing habits are retained without adding unselected template occurrences.
- Keep the event's actual time in `start`/`minutes`. Use `beforeMinutes` and `afterMinutes` for explicit buffers; use `null` when unspecified, and `0` only when supported by the request. For a train from 14:00 to 17:00 with one hour before and after, send `start: "14:00"`, `minutes: 180`, `beforeMinutes: 60`, `afterMinutes: 60`. Its reserved interval is 13:00–18:00. The host persists these buffers for subsequent plans and undo.
- Recognized habit occurrences are flexible automatically. For other handwritten calendar plans, only reclassify rows the user described as approximate or movable: read each standalone unchecked block and pass its `blockRef` in `flexibleRefs`. Otherwise use an empty array. The host releases an overlapping flexible time reservation while retaining an unchecked reminder. Do not reclassify unknown appointments, fixed-event rows, or completed records to force a fit.
- Two hard commitments (including buffers), or a hard commitment against protected completed history, remain a real conflict. Explain the tool result in that case. Report any omitted habits or pending work as displaced or unscheduled, not as failed creation of the fixed appointment. Preserve source tasks and habit definitions; do not infer completion, discard goals, or invent make-up times.
