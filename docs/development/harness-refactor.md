## 现有问题与证据

1. `src/daily.ts` 中 `taskSection` 只认一级 `# Tasks`，`appendTaskRows` 自动创建该标题，`organizeDailyTasks` 在没有明确移动请求时也会搬动原条目。
2. `src/transaction.ts` 在排程输出过程中调用 `organizeDailyTasks`，并为 AI 任务强制创建 master 条目。排程器与用户笔记组织方式因此相互影响。
3. `src/main.ts` 的 `scheduleAi` 将任务创建与排程绑定，没有可独立记录任意笔记内容的入口；没有可用时间块时直接拒绝新任务。此前底层事务测试对“无空闲时间也保存任务”的覆盖并不等于这条真实入口已支持该行为。
4. `src/llm.ts` 的 system prompt 直接写入目录、条目分类、用时估计、学习预算、餐后习惯等政策，再逐项新增 copy/revise/create 工具及关键词限制。
5. `skills/habits/SKILL.md` 通过 `src/habit-tool.ts` 和构建脚本打入 bundle。skill 与 TypeScript 同时规定文件名、固定标题和“一习惯一文件”，用户无法通过修改运行时 skill 来调整这些规则。
6. `src/llm.ts` 将读取结果返回模型，但遇到写动作后返回 `LlmReply`；`src/chat-view.ts` 随后在循环外执行写入。模型没有收到写工具成功、冲突、部分失败的真实结果。
7. 明确 undo 指令的本地快捷入口可以保留；通过扩大自然语言正则来替代通用执行循环不可持续。新增工具定义同样不能保证模型实际调用。

这些证据说明问题涉及内容结构、工具抽象和执行反馈；把 Tasks 换成一个可配置字符串只能解决其中很小一部分。

## 责任边界

| 层 | 应负责 | 不应负责 |
| --- | --- | --- |
| skill / 用户规则 | 理解目标；参考用户现有组织方式；决定标题、目录、分组、复制或修改方式；明确何时请求排程 | 扩大读写权限、绕过冲突检查、制造执行成功信息 |
| harness | 组装当前上下文与选定 skill；循环执行工具并返回结果；管理预算、取消、重试及完成状态 | 用用户自然语言关键词决定每一种业务操作；在传输代码中规定笔记布局 |
| Markdown 工具 | 发现笔记结构；读取选定内容；按读快照提供结构引用；暂存插入、替换和删除 | 将任意标题解释成固定任务类型；无请求地搬动列表 |
| scheduler / calendar adapter | 根据显式输入计算时间；渲染和解析 Day planner 兼容格式 | 规定普通笔记必须有 Tasks；创建或重排普通笔记时自动运行 |
| 事务宿主 | 授权范围、版本检查、变更清单、持久备份、串行提交、部分失败恢复和撤销 | 决定用户该用什么标题或如何分组 |

结构引用证明模型读取过某个快照，不等于获得了访问权限；每次读取或写入还要检查当前授权范围。通用编辑触及插件管理的 calendar 区域时，必须经适配器同步 tracking，或报告明确冲突，不能留下失配的管理状态。

固定的工具输入类型和兼容格式仍然必要。应解除的是业务内容布局与底层能力之间的绑定。

## 通用文档操作

初步工具集合按能力定义，最终名称可在实现阶段调整：

- `discover_notes`：在本轮允许的范围内按日期、文件名或查询定位笔记，返回文件引用和必要元数据。
- `read_note`：返回目录结构、用户指定段落或内容，以及绑定版本的 `documentRef`、`sectionRef` 和 `blockRef`。引用由宿主分配，不依赖标题唯一或任务名称不变。
- `stage_note_changes`：对已读取引用暂存插入、替换、删除。插入位置可以是已有段落、列表、文档末尾或显式创建的新段落；标题是数据。返回实际 diff、源/目标、增加/删除数量及变更集引用。
- `commit_changes`：提交一个已校验变更集，返回持久 operation ID、实际修改文件、结果状态和可撤销信息。
- `undo_operation`：恢复明确选中的最近一次事务，保留现有手动编辑保护；多步历史不是此次重构的必要前提。
- `plan_schedule`：只有用户要求分配时间时才调用，将经确认的任务/时间约束交给排程器；其 Day planner 输出也加入同一变更集。

“复制今天某一段到后面七天”由读取与七个插入操作组成，源文件不在写入集合中。“移动”需要显式源删除与目标插入。“记录待办”只插入清单；“安排时间”才进入排程器。不同组合共享工具与事务，不再为每个标题和自然语言动词增加专用工具。

笔记先解析现有结构：`# Tasks`、`## 待办`、`## Research` 或用户另一个标题都是普通文档结构。skill 可以提出默认格式，但宿主不会因标题不同而拒绝读取，也不会在重排时自动另建 Tasks。

## 真正的工具执行循环

```text
用户请求 + 所选 skill + 允许的上下文
    -> 模型提出工具调用
    -> 宿主校验并执行
    -> 将真实 tool_result 返回模型
    -> 模型继续读取、修订暂存变更或结束
    -> 界面显示由事务记录生成的执行状态
```

统一执行回执包括 `operationId`、`status`、`changedFiles`、`stateChanges`、`warnings` 和 `undoAvailable`。界面保留这些事实，即使提交后的模型请求失败，也不会丢失已写入记录。

每种提供商的请求/响应编码放在协议适配器中。适配器不识别 Tasks、复制、习惯或排程业务。统一循环处理工具注册、调用、错误和停止条件；不为不同提供商各维护一套业务状态机。

提交结果要区分：未写入、已提交、部分写入、失败。发生部分写入时保留恢复记录并停止后续写入；模型不能通过生成文字改变事务状态。工具失败应返回结构化原因，允许模型根据真实结果纠正参数或说明阻塞。循环有可配置的工具步数、上下文和时间预算，不使用固定“三次读取”来限制正常跨日操作。

本轮只出现文字时，界面明确显示“未修改文件”。即使文字声称完成，宿主也不显示成功状态。明确的命令快捷入口，例如 `/undo`（可保留精确的 `undo` 别名），可以作为同一个事务服务的快捷 UI。自然语言句子由模型和 skill 处理，不继续扩充“撤销刚才某事”一类正则分发。

## 运行时 skill

保留随插件发布的默认 skill，同时支持用户选择并编辑运行时 Markdown 版本，修改无需重新构建插件。运行时 skill 与普通笔记正文分别提供给模型；正文是数据，不能悄悄替换宿主政策。

默认 skill 分别描述笔记编辑、排程和习惯等工作方式。目录、标题、每个习惯单独存文件等作为可调整的建议或用户偏好，不作为所有用户都必须满足的校验条件。特定餐后步行示例可以放入示例文件，不进入每次请求的固定 system prompt。

宿主仍维护允许读取/写入的文件范围。通用读取能力不会默认把整个库发送到提供商：优先使用用户指定笔记、当前笔记、配置的资料范围与结构索引，再按需要读取相关段落。skill 可以指导如何组织和选择，不能自己扩大授权范围或读取插件凭据。

## 迁移顺序

1. **抽离事务服务和协议适配器**：统一 stage/commit/undo 与工具结果，保留现有备份格式和恢复能力。旧业务工具作为临时适配器，不立即废弃历史状态。
2. **接入通用 Markdown 结构与编辑**：用可读快照引用替换固定 Tasks 定位，先支持现有标题、列表、嵌套、frontmatter 和 CRLF 的精确编辑。
3. **实现通用 harness 与运行时 skill**：读和写都经过工具结果循环，显式显示本轮修改状态。删除 prompt 内的具体例程与自然语言关键词业务分发。
4. **拆开记录内容和排程**：普通编辑不运行 scheduler；排程只写其明确管理的 Day planner 输出和用户明确选中的内容位置。停用排程时自动搬动条目与强制 master 的逻辑。
5. **迁移旧数据与淘汰专用工具**：已有 `aiTasks`、tracking 和 undo 保留为兼容输入；识别旧 master 引用，不扫描全库搬文档、不以标题作为唯一身份、不自动复制或覆盖现有笔记。迁移通过变更集记录，可恢复。

方案涉及新的读写能力与笔记身份模型，因此应先明确实现范围，再修改核心流程。实现按此顺序推进，安装与验证状态记录在下游验证文件中。

## 验证标准

重点测试完整行为与执行结果，而不仅是 schema 与底层函数：

- 在 `# Tasks`、`## 待办`、自定义标题和不同段落层级下执行同一个复制请求，源文件字节一致，七个目标包含请求内容，Day planner 一致。
- 保存普通清单不调用 scheduler；只有明确安排时间时生成兼容的 clock rows。
- 修改一条内容时保留其他段落、嵌套结构、frontmatter 与换行格式；使用版本引用防止过期修改。
- 读、stage、commit、失败反馈及后续模型步骤通过真实 harness 入口验证；覆盖多提供商编码但复用业务逻辑。
- 模型仅输出文字、错误调用工具或忽略 undo 时，宿主不生成已执行状态；明确 undo 快捷入口实际恢复并验证原内容。
- 部分写入、重启、并发编辑、撤销冲突沿用已有证据，并针对新事务入口补充必要验证。
- 用户改动 skill 的组织方式后无需重新构建，普通笔记不能冒充 skill 或扩大权限。

此前 378 项全套测试及 32 项局部测试只能证明各自覆盖的旧路径。不能据此宣称本方案的新 harness 或真实意图理解已经通过验证。
